1. EXECUTIVE SUMMARY
================================================================

- Supports both VS Code DevContainer and direct tmux-based workflows

- Multiple permission modes (sketch/work/setup) for graduated trust
- Resumable sessions with tmux for interrupted workflow recovery

2.1 CONTAINER DEVELOPMENT ENVIRONMENTS
--------------------------------------
Key Finding: VS Code DevContainer specification is the industry standard

BEST PRACTICES IDENTIFIED:
- Hash-based workspace identification (SHA-256 of sorted labels)
- Multi-stage Dockerfile builds reduce image size by 60-70%
- Lifecycle hooks enable sophisticated initialization (onCreateCommand, postStartCommand, etc.)
- Features system allows modular capability addition
- Prebuild strategies reduce startup from 4-10 minutes to 5-10 seconds
- Named volumes outperform bind mounts 5-10x on macOS/Windows

RECOMMENDATIONS FOR BITBOT:
✓ Use stable hash-based container naming (already implemented)
✓ Implement lifecycle hooks for first-run setup
✓ Support features for optional capabilities
✓ Use multi-stage builds (already implemented)
✓ Consider prebuild/image caching for common configurations

IMPORTANT CLARIFICATION - Volumes vs Bind Mounts:
The research mentions named volumes are faster on macOS/Windows (5-10x), which is true
for general Docker usage. However, for BitBot's specific needs, BIND MOUNTS INSIDE THE
WORKSPACE are recommended:

✓ .bitbot/history/         - Shell history (travels with project)
✓ .bitbot/tmux-resurrect/  - Session persistence (travels with project)
✓ .bitbot/logs/            - Audit logs (travels with project)

WHY: These bind mounts are truly portable - when you clone/backup/migrate the workspace,
all state travels with it. Named volumes would require separate backup/restore and don't
integrate with Git/rsync/zip workflows.

EXCEPTION: Use named volumes only for truly container-specific state that shouldn't be
in the workspace (rare for BitBot's design)


2.2 AI AGENT SAFETY ARCHITECTURES
----------------------------------
Key Finding: Layered security is essential - no single defense is sufficient

SAFETY PATTERNS FROM INDUSTRY LEADERS:
- Claude Code: Sandboxed execution, read-only by default, patched CVEs
- Aider: Git-integrated safety net, automatic commits for rollback
- Cursor: Tiered permissions (auto-approve, prompt, always require approval)
- Devin: Fully sandboxed with human approval gates for critical operations
- GitHub Copilot Workspace: Cloud-based with explicit approval workflow

SECURITY FINDINGS:
⚠ 43% of MCP servers vulnerable to command injection (Backslash Security 2024)
⚠ 100% of MCP servers lacked authentication (Knostic research)
⚠ Denylist-based security easily bypassed (Cursor CVE-2024-0349)

DEFENSE IN DEPTH LAYERS:
1. Input validation (sanitize all AI inputs)
2. Allowlist-based permissions (not denylist)
3. Container isolation (Docker + optional gVisor/Firecracker)
4. Filesystem restrictions (read-only mounts, path validation)
5. Network isolation (egress filtering)
6. Syscall filtering (seccomp profiles)
7. Audit logging (OpenTelemetry standard)
8. Rollback mechanisms (Git auto-commits, snapshots)

RECOMMENDATIONS FOR BITBOT:
✓ Implement three-tier permission system (already planned: sketch/work/setup)
✓ Container isolation (already implemented)
✓ Add Git auto-commit safety net for rollback
✓ Implement audit logging for AI actions
✓ Use allowlist-based tool permissions
✓ Add dangerous operation detection (destructive commands, production access)


2.3 MODEL CONTEXT PROTOCOL (MCP)
---------------------------------
Key Finding: MCP is the emerging standard for AI tool integration

PROTOCOL ESSENTIALS:
- Three primitives: Tools (actions), Resources (data), Prompts (templates)
- Two client capabilities: Roots (filesystem context), Sampling (AI delegation)
- Transport layers: stdio (local), HTTP+SSE (remote)
- Message format: JSON-RPC 2.0

ARCHITECTURE PATTERNS:
- Client-side service discovery (MCP client discovers servers)
- Server-side registry (centralized service catalog)
- Gateway pattern (socat-based TCP routing)

SECURITY REQUIREMENTS:
- Zero trust model (authenticate everything)
- OAuth 2.0/OIDC for authentication
- Container isolation per MCP server
- Secrets management (never hardcode credentials)
- Input validation and sanitization

DEPLOYMENT PATTERNS:
- Local: subprocess via stdio
- Containerized: Docker Compose with health checks
- Remote: HTTP+SSE with load balancing

RECOMMENDATIONS FOR BITBOT:
✓ Dual-layer MCP architecture (already implemented)
  - Global MCP services: ports 8080/8090 (registry + gateway)
  - Workspace MCP services: ports 9080/9090 (registry + gateway)
✓ Service discovery via registry (already implemented)
✓ Docker Compose for service orchestration (already implemented)
⚠ Add authentication to MCP servers (not yet implemented)
⚠ Add input validation to all MCP tools (not yet implemented)

2.6 DOCKER-IN-DOCKER PATTERNS
------------------------------
Key Finding: Sysbox runtime provides secure DinD without privileged mode

SECURITY ANALYSIS:
⚠ Traditional DinD with --privileged gives root-level host access
⚠ Shared kernel means all nested containers can exploit kernel vulnerabilities
⚠ Container escapes possible via /proc, /sys manipulation

ALTERNATIVES EVALUATED:
- Kaniko: Builds images without Docker daemon (no privileged mode needed)
- BuildKit: Rootless builds, better caching
- Podman: Daemonless, rootless by default
- Sysbox: Runtime that enables secure system containers (best for DinD)

SECURITY RECOMMENDATIONS:
1. Maximum Security: Use Kaniko for image builds only
2. Recommended: Use Sysbox runtime for full Docker functionality without privileged
3. Development: Standard DinD DevContainer feature (requires privileged)
4. Simple: Docker socket mounting (fastest but least isolated)

RECOMMENDATIONS FOR BITBOT:
✓ Default: Docker socket mounting (already implemented) - good for MVP
⚠ Future: Add Sysbox support as optional security enhancement
⚠ Document security implications of Docker socket access
⚠ Add Kaniko support for builds without privileged mode

3.3 TBD: VS Code container reuse behavior
------------------------------------------
RESEARCH RESULT: VS Code DevContainer behavior

HOW VS CODE DETECTS EXISTING CONTAINERS:
1. Container naming: vsc-{folder-name}-{hash}
   - Hash based on: devcontainer.json path + devcontainer ID + local folder
2. Label matching: vsc.local.folder pointing to workspace
3. Running state check: Prefer running containers, can reuse stopped

VS CODE BEHAVIOR WHEN CONTAINER EXISTS:
- Running container: Attaches without restart
- Stopped container: Asks to restart or rebuild
- Missing container: Creates new one

INTEGRATION WITH BITBOT:
- Use compatible naming: bitbot-dev-{workspace-hash}
- Add labels for VS Code compatibility:
  vsc.local.folder: /workspace/path
  vsc.quality: stable
  devcontainer.local_folder: /workspace/path
  devcontainer.config_file: /workspace/.devcontainer/devcontainer.json

WORKFLOW:
1. User runs `bitbot` in terminal → creates/attaches to container
2. User opens VS Code → VS Code detects existing container via labels
3. VS Code attaches to same container
4. All terminals share the same container environment

TERMINAL OPTIONS IN VS CODE:
- Default terminal: Opens inside devcontainer automatically
- Bitbot terminal: Add VS Code task that runs `bitbot` command


3.4 TBD: Parent workspace context inheritance
----------------------------------------------
RESEARCH RESULT: Monorepo patterns and nested workspace handling

USE CASES:
- Monorepo: /project → /project/service-a, /project/service-b
- Nested projects: /client → /client/packages/ui
- Shared configuration: parent .gitignore, .editorconfig, etc.

IMPLEMENTATION OPTIONS:

OPTION 1: Inherit Parent MCP Services (RECOMMENDED)
- Child workspace can access parent's MCP services
- Parent MCP services exposed via network to child containers
- Environment variable: BITBOT_PARENT_MCP=tcp://parent-ip:9090

OPTION 2: Shared Configuration Volume
- Mount parent workspace as read-only: /parent:ro
- Child can reference parent configs: /parent/.eslintrc
- Opt-in via: bitbot --inherit-parent

OPTION 3: Context Linking
- Create .bitbot/parent symlink → parent workspace
- CLI flag: bitbot --parent-context
- Parent's global config accessible but not workspace

SECURITY CONSIDERATIONS:
⚠ Parent access increases attack surface
⚠ Only allow read-only access to parent
⚠ Require explicit opt-in (not automatic)

RECOMMENDATION:
- Start without parent context (simpler)
- Add as advanced feature in v2
- Document monorepo patterns using shared global MCP services


3.5 TBD: Docker access separation for BitBot components vs user workflows
--------------------------------------------------------------------------
RESEARCH RESULT: Namespace isolation and Sysbox runtime

CHALLENGE:
- BitBot needs Docker for MCP containers
- User needs Docker for workflows (builds, tests, etc.)
- Want to prevent user from breaking BitBot's containers

IMPLEMENTATION STRATEGIES:

OPTION 1: Docker Socket Sharing (Current Implementation)
✓ Simple: Mount same Docker socket
✓ Fast: Direct access, no overhead
✗ No Isolation: User can see/kill BitBot containers
✗ Security: Full Docker access = root on host

OPTION 2: Docker Context Separation (RECOMMENDED)
- Two Docker contexts: "bitbot" and "user"
- BitBot containers tagged: com.bitbot.managed=true
- Wrapper script filters docker commands
- User context excludes BitBot-managed containers

Example:
```bash
# BitBot internal
docker --context bitbot compose up mcp-registry

# User workflow (filtered)
bitbot docker build .  # Wrapper filters out bitbot containers
```

OPTION 3: Nested Docker with Sysbox (Maximum Isolation)
- BitBot uses host Docker via context
- User gets separate Docker daemon inside container
- Full isolation, but requires Sysbox runtime
- More complex setup

OPTION 4: Two Docker Sockets
- Host Docker socket: /var/run/docker.sock (BitBot only)
- User Docker socket: DinD inside container at /var/run/docker-user.sock
- Environment variable: DOCKER_HOST=unix:///var/run/docker-user.sock

RECOMMENDATION FOR BITBOT:
Phase 1 (MVP): Docker socket sharing (current)
  - Document that user has full Docker access
  - Namespace BitBot containers: bitbot-*
  - Add protection wrapper: bitbot docker ... (filtered commands)

Phase 2 (Enhanced): Docker context separation
  - Wrapper script enforces context
  - Protect BitBot-managed containers
  - User-friendly error messages

Phase 3 (Advanced): Sysbox runtime option
  - Full isolation for security-conscious users
  - Document as advanced setup

4.1 PRIMARY COMMAND: bitbot
----------------------------

USAGE:
  bitbot [OPTIONS] [COMMAND] [ARGS...]

GLOBAL OPTIONS:
  --mode MODE          Container mode: sketch, work, setup (default: work)
  --resume            Resume existing session (skip session picker)
  --new               Force new session (skip session picker)
  --rebuild           Rebuild container image before starting
  --pull              Pull latest base image before starting
  --detach, -d        Start container in detached mode
  --help, -h          Show help message
  --version, -v       Show version information
  --debug             Enable debug logging

COMMANDS:
  (default)           Enter workspace container (starts if needed, shows session picker)
  init                Initialize workspace for BitBot
  start               Start workspace container
  stop                Stop workspace container
  restart             Restart workspace container
  rm                  Remove workspace container
  logs                Show container logs
  status              Show workspace status (container running, sessions, etc.)
  sessions            List tmux sessions in container
  attach [SESSION]    Attach to specific tmux session
  exec COMMAND        Execute command in container
  update              Update BitBot to latest version
  config              Manage BitBot configuration
  mcp                 Manage MCP services (list, start, stop, add)
  docker [ARGS...]    Run Docker command (filtered to protect BitBot containers)
  setup               Run first-time setup wizard

EXAMPLES:
  # Start BitBot in current workspace (default work mode)
  bitbot

  # Start in sketch mode (limited write access)
  bitbot --mode sketch

  # Start in setup mode (full access to .devcontainer)
  bitbot --mode setup

  # Resume last session without picker
  bitbot --resume

  # Force new session
  bitbot --new

  # Initialize new workspace
  bitbot init

  # Check status
  bitbot status

  # List sessions
  bitbot sessions

  # Attach to specific session
  bitbot attach session-name

  # Run command in container
  bitbot exec ls -la

  # Manage MCP services
  bitbot mcp list
  bitbot mcp start simple-mcp
  bitbot mcp add filesystem ./mcp-filesystem

  # Use Docker safely
  bitbot docker ps
  bitbot docker build -t myapp .

  # Update BitBot
  bitbot update

6.0 LEVERAGING OFFICIAL DEVCONTAINER TOOLS
-------------------------------------------

IMPORTANT DISCOVERY: Official tools exist for devcontainer management from CLI

OPTION 1: @devcontainers/cli (Official Microsoft Reference Implementation)
--------------------------------------------------------------------------
Repository: https://github.com/devcontainers/cli
Package: npm install -g @devcontainers/cli

WHAT IT PROVIDES:
✓ Official reference implementation of Dev Containers spec
✓ devcontainer up - spins up containers with devcontainer.json settings
✓ devcontainer exec - executes commands with proper env/user context
✓ devcontainer build - builds/pre-builds container images
✓ devcontainer read-configuration - outputs workspace settings
✓ Lifecycle management for postCreateCommand, etc.
✓ Same behavior as VS Code Remote-Containers

KEY COMMANDS:
  devcontainer up --workspace-folder .
  devcontainer exec --workspace-folder . bash
  devcontainer build --workspace-folder .

PROS FOR BITBOT:
✓ Official, standards-compliant tool
✓ Maintained by VS Code/DevContainers team
✓ Lightweight (npm package)
✓ Full control over session management layer
✓ Less maintenance burden (Docker orchestration handled)
✓ Direct devcontainer.json support

CONS:
✗ No built-in tmux/session management
✗ Less abstraction (closer to raw Docker)
✗ No workspace management features
✗ Requires Node.js/npm


OPTION 2: DevPod (Loft Labs)
-----------------------------
Website: https://devpod.sh
Repository: https://github.com/loft-sh/devpod

WHAT IT PROVIDES:
✓ High-level devcontainer workspace manager
✓ Multi-backend support (local Docker, SSH, cloud providers)
✓ Desktop GUI + CLI
✓ Workspace lifecycle management
✓ Auto-shutdown, prebuilds, credential sync
✓ Cross-IDE compatibility (VS Code, JetBrains, SSH)
✓ Client-only (no server backend)
✓ 5-10x cheaper than GitHub Codespaces

KEY COMMANDS:
  devpod up .                    # Start workspace
  devpod ssh default             # SSH into workspace
  devpod list                    # List workspaces
  devpod stop default            # Stop workspace

PROS FOR BITBOT:
✓ Higher-level workspace abstraction
✓ Built-in workspace management
✓ Multi-backend flexibility
✓ Active development and community

CONS:
✗ Additional layer of abstraction
✗ Less direct control
✗ Still no native tmux session management
✗ Heavier dependency

7. SECURITY & SAFETY ARCHITECTURE
================================================================

7.1 THREAT MODEL
----------------

THREATS IN SCOPE:
1. AI agent generates malicious code (intentional or hallucinated)
2. AI agent accidentally deletes important files
3. AI agent modifies .devcontainer breaking environment
4. User runs AI in YOLO mode without understanding risks
5. MCP service vulnerability exploited by AI
6. Supply chain attack via malicious MCP server

THREATS OUT OF SCOPE:
1. Compromised Docker daemon on host
2. Host kernel vulnerabilities
3. Physical access to machine
4. Social engineering of user


7.2 DEFENSE LAYERS
------------------

LAYER 1: INPUT VALIDATION
- Sanitize all AI inputs before execution
- Validate file paths (no ../ escapes, no /etc access)
- Validate commands (no rm -rf /, no dd if=/dev/zero)

LAYER 2: ALLOWLIST-BASED PERMISSIONS
- Allowed tools: git, npm, dotnet, common dev tools
- Denied tools: curl | bash, eval, exec without review
- Configurable per workspace: .bitbot/allowed-tools.json

LAYER 3: CONTAINER ISOLATION
- Docker container as primary boundary
- Limited capabilities (drop CAP_SYS_ADMIN, etc.)
- Seccomp profile to restrict syscalls

LAYER 4: FILESYSTEM RESTRICTIONS
- Mode-based mount permissions (sketch/work/setup)
- Read-only .devcontainer in work mode
- Path validation in AI tool calls

LAYER 5: NETWORK ISOLATION
- Egress filtering in sketch mode (no internet)
- MCP services only accessible via localhost
- No production database access from dev containers

LAYER 6: SYSCALL FILTERING
- Seccomp profiles per mode
- Block dangerous syscalls: ptrace, mount, reboot

LAYER 7: AUDIT LOGGING
- Log all AI actions with timestamps
- Log mode switches with reason
- Log MCP tool invocations
- Structured JSON format for analysis

LAYER 8: ROLLBACK MECHANISMS
- Git auto-commits before AI operations
- Snapshots before destructive operations
- Easy rollback: bitbot rollback [timestamp]


7.3 DANGEROUS OPERATION DETECTION
----------------------------------

COMMAND ANALYSIS:
- Regex patterns for destructive commands
- Behavioral anomaly detection (too many files modified)
- Step-up authentication for high-risk operations

ALWAYS REQUIRE CONFIRMATION:
✓ rm -rf, rm *
✓ DROP TABLE, DELETE FROM without WHERE
✓ git push --force to main/master
✓ Production deployments (kubectl apply, terraform apply)
✓ Modifying .bitbot/ or .devcontainer/
✓ Installing system packages (apt, yum)

AUTO-APPROVE IN WORK MODE:
✓ File edits in workspace
✓ Git commits, branch creation
✓ Running tests
✓ Starting dev servers
✓ Installing project dependencies (npm install, dotnet restore)

DENY IN SKETCH MODE:
✗ Any filesystem writes outside /sketch
✗ Network access
✗ Docker commands
✗ MCP tool calls

8.3 WINDOWS INSTALLATION
-------------------------

WINDOWS .EXE WRAPPER (Go):
```go
// bitbot.exe - Minimal Windows wrapper
package main

import (
    "os"
    "os/exec"
    "path/filepath"
)

func main() {
    // Get directory of this executable
    exePath, _ := os.Executable()
    exeDir := filepath.Dir(exePath)
    scriptPath := filepath.Join(exeDir, "bitbot")

    // Run in WSL
    cmd := exec.Command("wsl", "bash", scriptPath)
    cmd.Args = append(cmd.Args, os.Args[1:]...)
    cmd.Stdin = os.Stdin
    cmd.Stdout = os.Stdout
    cmd.Stderr = os.Stderr

    if err := cmd.Run(); err != nil {
        os.Exit(1)
    }
}
```

Build command:
GOOS=windows GOARCH=amd64 go build -o bitbot.exe -ldflags "-s -w" bitbot.go

SIZE: ~1-2MB statically linked Go executable
