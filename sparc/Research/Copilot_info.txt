RESEARCH FINDINGS & GAP ANALYSIS:
----------------------------------

BB Command Shorthand Research:
- "bb" is used by BitBucket CLI tool, but not widely adopted
- Alternative: "bt" (bitbot) or keep "bitbot" for clarity
- Recommendation: Start with "bitbot", add "bb" alias later if desired

PATH Setup & Installation:
- Windows: Add to both System PATH and WSL PATH
- Location: /mnt/c/BitBot/global/bitbot (accessible from both environments)
- First run: bitbot install creates shortcuts, PATH entries, WSL integration
- Auto-detection: Check if running in WSL vs native Windows/Mac/Linux

VS Code DevContainer Integration Research:
- VS Code detects existing containers via .devcontainer/devcontainer.json
- If container already running: VS Code connects to existing instance
- Container reuse: VS Code "Attach to Running Container" workflow
- Terminal integration: All VS Code terminals auto-route to container

Terminal History Persistence:
- VS Code stores terminal history in workspace .vscode/settings.json
- BitBot approach: Mount ~/.bash_history per workspace hash
- Location: .bitbot/terminal-history/ with workspace-specific files

Docker-in-Docker Separation Strategy:
- BitBot Docker: Uses host Docker socket (/var/run/docker.sock)
- User Docker: Separate Docker-in-Docker daemon in container
- Network isolation: BitBot containers on isolated network
- Volume separation: BitBot volumes vs user development volumes

PROPOSED BITBOT ARGUMENTS:
----------------------------------

Core Operations:
bitbot                    # Smart launch - resume or new session
bitbot new                # Force new session
bitbot resume [name]      # Resume specific session
bitbot list               # List active sessions/containers
bitbot stop [name]        # Stop specific session
bitbot kill               # Stop all BitBot containers

Quick Mode Selection:
bitbot sketch             # Restricted mode - /sketch write only
bitbot work               # Default mode - workspace except .devcontainer
bitbot setup              # Full access mode

Agent Selection:
bitbot claude             # Claude Code agent
bitbot open               # OpenCode agent
bitbot custom [name]      # Custom agent

Configuration:
bitbot config             # Interactive configuration wizard
bitbot install            # Setup PATH and integrations
bitbot doctor             # System diagnostics
bitbot version            # Version information

Templates:
bitbot template [name]    # Apply workspace template
bitbot templates          # List available templates

Advanced:
bitbot logs [service]     # View logs (agent, mcp, container)
bitbot shell              # Direct container shell access
bitbot export             # Export workspace configuration
bitbot import [file]      # Import workspace configuration

3. Language Runtimes: Node.js, Python, .NET Core, Go

Volume Mount Strategy:
- Workspace: /workspace (project files)
- BitBot Config: /opt/bitbot (read-only BitBot scripts)
- Agent Config: /home/bitbot/.config (agent configurations)
- Terminal History: /home/bitbot/.bash_history (persistent)
- Docker Socket: /var/run/docker.sock (Docker access)

NETWORK ARCHITECTURE:
----------------------------------

Network Separation:
- bitbot-global: 172.20.0.0/16 (global MCP services)
- bitbot-workspace-{hash}: 172.21.x.0/24 (workspace services)
- docker-user: 172.22.0.0/16 (user Docker workflows)
- Bridge networks for controlled inter-network communication

Port Allocation:
- Global MCP Registry: 8080
- Global MCP Gateway: 8090
- Workspace MCP Registry: 9080
- Workspace MCP Gateway: 9090
- User applications: 3000-3999, 8000-8999

Security Policies:
- Sketch mode: No external network access except AI agent
- Work mode: Standard internet access, no BitBot network access
- Setup mode: Full network access including BitBot networks
